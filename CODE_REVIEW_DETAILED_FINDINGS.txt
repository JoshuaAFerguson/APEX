ISSUE 2: JSON SERIALIZATION LOSES DATE OBJECT TYPE
┌─────────────────────────────────────────────────────────────────────────┐
│ SEVERITY: HIGH / BLOCKING                                               │
│ FILE: packages/api/src/__tests__/mcp-error-broadcasting.integration.test.ts
│ LINES: 92 (broadcast), 327 & 344 (test expectations)                    │
└─────────────────────────────────────────────────────────────────────────┘

DESCRIPTION:
  When events are serialized via JSON.stringify() for WebSocket transmission,
  Date objects are converted to ISO 8601 strings. However, test assertions
  expect Date objects using expect.any(Date).

CURRENT CODE (Line 92 - Broadcast):
  const message = JSON.stringify(event);  // ← Converts Date → String

CURRENT CODE (Line 327 - Test Expectation):
  timestamp: expect.any(Date),  // ← Expects Date object

ACTUAL TRANSMISSION:
  Input: { timestamp: new Date('2026-03-14...') }
  After JSON.stringify: { timestamp: "2026-03-14T11:09:30.787Z" }
  After JSON.parse: { timestamp: "2026-03-14T11:09:30.787Z" } ← Still string!

TEST FAILURE OUTPUT:
  Expected: timestamp: Any<Date>
  Received: timestamp: "2026-03-14T11:09:30.787Z"

  Expected: errorOccurredAt: Any<Date>
  Received: errorOccurredAt: "2026-03-14T11:09:30.787Z"

ROOT CAUSE:
  JSON.stringify() and JSON.parse() don't preserve Date type. This is
  fundamental JSON behavior. Test expectations were based on incorrect
  assumptions about JSON transmission.

FIX APPLIED (Lines 324-360):
  Changed from deep equality check with expect.any(Date) to explicit
  field-by-field validation:

  OLD:
    expect(event).toEqual({
      timestamp: expect.any(Date),
      ...
    });

  NEW:
    expect(event.type).toBe('mcp:error');
    expect(typeof event.timestamp).toBe('string');
    expect(() => new Date(event.data.errorOccurredAt)).not.toThrow();

VERIFICATION:
  ✅ Test now passes: "delivers MCP error events to connected WebSocket clients"
  ✅ Validates ISO 8601 string format
  ✅ Verifies strings are parseable as dates
  ✅ More accurate representation of actual behavior

ISSUE 4: UNGUARDED JSON.PARSE IN MESSAGE HANDLER
┌─────────────────────────────────────────────────────────────────────────┐
│ SEVERITY: MEDIUM / NON-BLOCKING                                         │
│ FILE: packages/api/src/__tests__/mcp-error-broadcasting.integration.test.ts
│ LINES: 318-320 (in WebSocket message handler)                           │
│ STATUS: DOCUMENTED, NOT FIXED                                           │
└─────────────────────────────────────────────────────────────────────────┘

DESCRIPTION:
  JSON parsing errors are not properly handled in WebSocket message handler.

CURRENT CODE:
  ws.on('message', (data) => {
    const event = JSON.parse(data.toString());  // ← Unguarded parse!
    receivedEvents.push(event);
  });

FAILURE SCENARIO:
  1. WebSocket receives malformed JSON: "{invalid json}"
  2. JSON.parse() throws SyntaxError
  3. No error handler - message event aborts
  4. Test may hang waiting for event that never arrives

ALSO IN FILE (Lines 144-151):
  socket.on('message', (data) => {
    try {
      const event = JSON.parse(data.toString());
      receivedEvents.push(event);
    } catch (error) {
      console.error('Failed to parse WebSocket message:', error);  ← Silent
    }
  });

ISSUE:
  Error is only logged to console, not tracked for test assertions.
  No test coverage for malformed message handling.

RECOMMENDATION:
  Explicit error tracking for test visibility:

  ws.on('message', (data) => {
    try {
      const event = JSON.parse(data.toString());
      receivedEvents.push(event);
    } catch (error) {
      // Track parse errors explicitly
      receivedEvents.push({
        _parseError: true,
        error: error.message,
        rawData: data.toString()
      });
      reject(error);  // Fail test explicitly
    }
  });

ISSUE 6: MISSING TEST TIMEOUT CONFIGURATIONS
┌─────────────────────────────────────────────────────────────────────────┐
│ SEVERITY: LOW / ENHANCEMENT                                             │
│ FILE: mcp-error-broadcasting.integration.test.ts                        │
│ LINES: 312, 380, 455, 616 (async test functions)                        │
│ STATUS: DOCUMENTED, NOT FIXED                                           │
└─────────────────────────────────────────────────────────────────────────┘

DESCRIPTION:
  Several async tests rely on manual setTimeout for timeout, but don't
  have explicit Vitest timeout configuration.

CURRENT PATTERN:
  it('test name', async () => {  // ← No timeout config
    await new Promise<void>((resolve, reject) => {
      // ...
      setTimeout(() => reject(new Error('Test timeout')), 5000);
    });
  });

ISSUE:
  - If test never reaches setTimeout call, it hangs indefinitely
  - Hard to identify hanging tests in CI/CD
  - No guaranteed WebSocket cleanup

RECOMMENDATION:
  it('test name', { timeout: 10000 }, async () => {  // Add config
    try {
      await new Promise<void>((resolve, reject) => {
        // ...
      });
    } finally {
      ws?.close();  // Guarantee cleanup
    }
  });

ISSUE 7: INCOMPLETE EVENT ORDERING VERIFICATION
┌─────────────────────────────────────────────────────────────────────────┐
│ SEVERITY: LOW / ENHANCEMENT                                             │
│ FILE: mcp-error-broadcasting.integration.test.ts                        │
│ LINES: 616-668 (rapid succession test)                                  │
│ STATUS: DOCUMENTED, NOT FIXED                                           │
└─────────────────────────────────────────────────────────────────────────┘

DESCRIPTION:
  Rapid event test validates count but not ordering, completeness, or
  absence of duplicates.

CURRENT VALIDATION:
  if (receivedEvents.length === errorCount) {
    receivedEvents.forEach((event, index) => {
      expect(event.data.serverId).toBe(`rapid-test-${index}`);
    });
  }

GAPS:
  - Assumes events arrive in order (not guaranteed under load)
  - No duplicate detection
  - No timing distribution analysis
  - No validation of payload completeness

RECOMMENDATION:
  Enhanced verification:

  receivedEvents.forEach((event, index) => {
    expect(event.data.serverId).toBe(`rapid-test-${index}`);

    // Verify no duplicates
    const sameId = receivedEvents.filter(
      e => e.data.serverId === event.data.serverId
    ).length;
    expect(sameId).toBe(1);

    // Verify complete payload
    expect(event.type).toBe('mcp:error');
    expect(event.timestamp).toBeDefined();
    expect(event.data.error).toBeDefined();
  });
